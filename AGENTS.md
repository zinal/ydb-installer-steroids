# Инструкции для агентов

Этот репозиторий — площадка совместной доработки удобного инсталлятора YDB. Каталоги `ansible-collection/`, `ansible-examples/` и `installer/` — рабочие копии чужих проектов, а не канонические деревья.

Канонические версии живут в основных репозиториях организации `ydb-platform`. Любой анализ и любая правка делаются с расчётом, что результат позже будет слит в соответствующий основной репозиторий отдельным pull request. Расхождение с основным репозиторием — долг переноса, а не право уводить копию в сторону.

Корневой `AGENTS.md` относится только к этой площадке. В основные репозитории его не переносить. Правила кода внутри копии (сейчас это `installer/AGENTS.md`) остаются в силе для своего дерева и не отменяют требование обратного слияния.

## Куда что сливать

| Каталог на площадке | Основной репозиторий | Что это |
| --- | --- | --- |
| `ansible-collection/` | https://github.com/ydb-platform/ydb-ansible | Коллекция Ansible `ydb_platform.ydb` (`galaxy.yml`: namespace `ydb_platform`, name `ydb`) |
| `ansible-examples/` | https://github.com/ydb-platform/ydb-ansible-examples | Примеры inventory, топологий и сценариев эксплуатации |
| `installer/` | https://github.com/ydb-platform/ydb-installer | Инсталлятор: Go API и Vue-интерфейс |

Ветка слияния по умолчанию у всех трёх — `main`. Лицензия копий — Apache-2.0; при переносе её не менять.

Коллекция `ydb_platform.ydb_em` в эту площадку не скопирована. Её основной репозиторий — https://github.com/ydb-platform/ydb-em , каталог `ansible/ydb_platform/ydb_em`. Не описывать и не «чинить» EM-плейбуки так, будто их исходники лежат рядом.

## Как анализировать

1. Определить дерево по таблице выше. Файл за пределами трёх каталогов относится к площадке, а не к основному репозиторию.
2. Отделить поведение уже выпущенного `main` от поведения рабочей копии. Для коллекции это разные деревья: базовый `37fdaa87…` и копия с дельтой `prepare-2.2.0`.
3. Перед выводом «так устроено в проекте» открыть тот же файл в текущем `main` основного репозитория. Копия могла устареть или, наоборот, содержать ещё не слитые правки.
4. Идти по контракту, а не по каталогу. Имя плейбука, переменная inventory, флаг CLI и поле API могут читаться из второго дерева. Проверить соседей, прежде чем менять имя или форму.
5. Примеры не являются реализацией ролей. Инсталлятор не является спецификацией плейбуков: он их вызывает и пишет inventory.
6. Штатная сборка runtime внутри `installer/` берёт `ydb_platform.ydb` из git: в `installer/scripts/runtime.lock` заданы `COLLECTION_GIT_URL=git+https://github.com/ydb-platform/ydb-ansible` и `COLLECTION_GIT_REF=main`. Локальный запасной путь там — `COLLECTION_LOCAL_PATH=../ydb-ansible`; каталог площадки называется `ansible-collection/` и сам по себе в эту сборку не подставляется. Собрать инсталлятор с плейбуками из этой площадки: `scripts/build-installer.sh` (или `make build`) из корня. Скрипт на время сборки очищает `COLLECTION_GIT_URL`, передаёт `COLLECTION_LOCAL_PATH` на `ansible-collection/` и возвращает lock-файл байт в байт. Ссылку в lock-файле на эту площадку постоянным источником не делать и сам lock-файл ради этого не править. Правка коллекции попадает в бинарник после этого запуска либо после слияния в основной репозиторий и пересборки runtime с новым `COLLECTION_GIT_REF`. Если инсталлятор зависит от ещё не слитой правки коллекции, в отчёте указать порядок: сначала коллекция, затем SHA или тег, на который встанет `COLLECTION_GIT_REF`.

Проверка расхождения с основными репозиториями:

```bash
git clone --depth 1 https://github.com/ydb-platform/ydb-ansible.git /tmp/ydb-ansible
diff -rq /tmp/ydb-ansible ansible-collection --exclude __pycache__

git clone --depth 1 https://github.com/ydb-platform/ydb-ansible-examples.git /tmp/ydb-ansible-examples
diff -rq /tmp/ydb-ansible-examples ansible-examples
```

Для инсталлятора ту же проверку выполнить, когда https://github.com/ydb-platform/ydb-installer доступен. Пока URL недоступен, анализ ограничивать деревом `installer/` и не утверждать, что оно совпадает с `main`.

Если обновляешь саму копию из основного репозитория, в том же изменении обнови SHA в этом файле. Несовпадение копии с записанным SHA без такой правки — ошибка учёта, а не новое исследование.

## Как редактировать, чтобы результат можно было слить

Каждое изменение проектируется как будущий pull request в один основной репозиторий.

- Один логический коммит — одно дерево и одна причина. Сообщение писать так, чтобы его можно было перенести в основной репозиторий: зачем изменение, без отсылок к этой площадке.
- Файлы между `ansible-collection/`, `ansible-examples/` и `installer/` не перемешивать. Общий контракт менять в каждой затронутой копии, но в отчёте разложить это на отдельные upstream PR и указать порядок слияния.
- Сохранять раскладку каталогов, имена плейбуков, переменные inventory, публичные флаги и API. Несовместимое изменение допустимо только как осознанный контракт основного репозитория и должно быть названо в отчёте.
- Стиль брать из файла, который редактируешь. Попутный рефакторинг, переформатирование несвязанных файлов и смена лицензионных заголовков затрудняют перенос — не делать их.
- Тесты основного репозитория не удалять. Новый тест должен быть уместен в том же репозитории, а не только на этой площадке.
- Секреты, боевые inventory, `__pycache__` и локальные кэши не коммитить.
- Номера версий не объявлять релизом основного репозитория. `2.2.0` в `galaxy.yml` и `v0.4.3` в инсталляторе не повышать и не тегировать здесь. Менять номер только если это часть согласованного переноса и номер не сталкивается с уже существующим тегом upstream.
- В основные репозитории не пушить и pull request туда не открывать, пока это явно не поручено. Готовить перенос, а не выполнять его самостоятельно.
- Корневой `AGENTS.md` и любые другие файлы, описывающие только эту площадку, в патч для основного репозитория не включать.

Патч для основного репозитория из коммитов площадки, затрагивающих один каталог:

```bash
git diff <base> -- ansible-collection \
  | sed -e 's|a/ansible-collection/|a/|' -e 's|b/ansible-collection/|b/|'
```

Для `ansible-examples/` и `installer/` подставить свой префикс. Перед тем как считать патч готовым, наложить его на свежий `main` основного репозитория и записать, встал он чисто или какие файлы конфликтуют. Конфликт с коммитами, пришедшими в `main` после baseline, разрешать в пользу осмысленного объединения, а не перезаписью upstream.

## Что писать в итоге задачи

Заканчивать отчёт блоком:

```
Обратное слияние:
- репозиторий:
- база, с которой сверено (ветка и SHA):
- файлы:
- патч ложится на текущий main: да или нет; какие конфликты:
- зависимость от другого дерева и порядок слияния:
- что в основной репозиторий не переносить:
```

Если правка ни одного из трёх деревьев не касается, в блоке так и написать: перенос не требуется.
